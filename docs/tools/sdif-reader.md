The SDIF file reader opens a file in the [SDIF](../software/sdif.md) swimming data format and shows what
it holds: the meet, its teams, every individual and relay result with splits, each record
decoded field by field, a check against the version 3 specification, and CSV exports of the
results.[^spec] It also reads Hy-Tek [CL2](../software/cl2.md) files, which use the same record
layout.

The file is read inside your browser. It is not uploaded, sent anywhere or saved, and closing
the page discards it. That is deliberate: SDIF files contain swimmers' names, birth
dates and registration numbers.

## Using it

Drop a file on the box above or choose one from your computer. Meet management programs
write SDIF results as `.sd3` files, and Hy-Tek exports contain a `.cl2` beside the `.hy3`.
The `.zip` that Meet Manager produces can be opened as it is, without unzipping it first,
and so can a zip of several such exports. Where an archive offers more than one SDIF
file, the reader lists them for you to pick. The sample file is an invented two-team meet, useful for
seeing what each view does; it contains one deliberate fault for the validator to find.

Files that are not SDIF get a short explanation instead of a list of errors. That covers
a `.hy3` (a different Hy-Tek format), a PDF of results, a web page saved in place of a
download, a Lenex or other XML file, and a file saved from a spreadsheet as UTF-16
"Unicode", which meet programs refuse and which needs saving again as plain text.

The reader has four views:

- Meet lists the teams, then each event with its swims in place order, with heat, lane,
  points, splits and relay legs. In a meet with prelims and finals, each round is listed
  separately with its own places. A large meet starts with its events closed.
- Records shows every line of the file. Opening one lays out each field with its position,
  its raw characters (spaces drawn as dots) and what the value means, using the code tables
  at the back of the specification.
- Validation lists what does not follow the specification, graded as errors, warnings and
  notes. Each finding links to the record it concerns.
- Export writes the individual results, relay results and splits as CSV files for a
  spreadsheet.

## What it checks

The validator applies the rules a program importing the file relies on:[^spec]

- The file opens with an `A0` record and closes with a `Z0`, and every record type is one
  of the sixteen the specification defines.
- Each record is 160 characters of data. Shorter lines, usually the result of an editor
  trimming trailing spaces, are read as if padded and noted.
- Fields marked M1 are filled in. Blank M2 fields, which USA Swimming's own processing
  needs but meet programs often leave empty, are counted and reported as notes.
- Times have the `mm:ss.hh` shape or one of the status codes (NT, NS, DNF, DQ, SCR),
  dates are real MMDDYYYY dates, and coded fields hold a value from their table.
- A time is followed by its course code, swims come after a team record, and splits come
  after a swim.
- The record counts in the `Z0` terminator agree with the file.
- A relay's count of the swimmer records that follow it is right, swimmers are entered in
  events for their own sex unless the event is mixed, swim dates fall within the meet's
  dates, and birth dates come before swim dates.
- Split records hold as many times as they say. A shortfall, usually a missed split touch,
  is reported as a note.
- The file has line breaks, starts with the `A0` record itself rather than a byte-order
  mark, and uses one byte per character.

Two results are reported as notes rather than faults, because the specification does not
settle them. A `Z0` that counts only the `D0` records as "D records" is a reading at least
one widely used program takes, as the [SDIF](../software/sdif.md) page describes. The same program
counts "G records" as one per swim with splits rather than one per split record, so a long
race that needs several split records is counted once. A stroke code of `H`
is not in the specification's table, but some meet programs use it for diving, with the
score written where a time would go, and for relays the table has no code for. The reader
shows those scores as scores and reports the code once, with a count, as a warning with
that explanation. Repeated findings of other kinds are grouped the same way.

Meet Manager also writes its own data into columns the specification reserves for future
use. That is reported once per file as a note.

In the same way, a relay swimmer's prelim and swim-off leg fields are left blank by meets
that had no prelims or swim-offs. Only a swimmer with no leg order for any round is
reported.

For a CL2 file the reader also tests each record's checksum against the algorithm
published for that format, as described on the [CL2](../software/cl2.md) page. Only the two checksum
digits are compared, because the published rule for the two characters before them is
known to be incomplete.

## Limits

The reader follows version 3 of the specification, dated 28 April 1998, which is the
version files still declare.[^spec] It reads files and does not write or repair them. Code
tables are the specification's own, so country and LSC codes added after 1998 show as not
in the table. The [HY3](../software/hy3.md) format and the XML forms ([XSDIF](../software/xsdif.md),
[Lenex](../software/lenex.md)) are different formats and are not read here.
